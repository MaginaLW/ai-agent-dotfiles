# 需要实际修改或执行时读取

本文件只补充旧规则修订与 Git 执行；不授予权限，也不要求已经明确授权的 Git 或部署链重新发问、重新规划或重复完整审查。任务的原始有效指令和平台正式机制决定能做什么，反馈台账仅提供来源线索。

## 旧规则修订

发现已证实的重复询问，或真实低分指向已知、可修改且将再次打断的逐轮条款时，主动推进到具体提案；不要用“存在冲突”或“必要确认”结束排查，也不要为了提案凑评分。

本任务已有同类低分、下一动作又将触发相同条款时，就在该次发问前准备提案；尚无下一动作时在正常收尾处理，无需等待三个独立任务。把“本次执行许可”和“规则修订许可”分别列清，可合并呈现，不能靠许可其中一项推定另一项。用户已批准的修订按原范围落实，不为同一决定再次发问。

1. **找真实源。** 引用造成当前打断的文件条款、实际加载关系、范围与例子。区分源文件、生成／live 副本、历史提议及不能修改的上层要求。不确定就只查相关来源，不批量改所有同名文件。
2. **准备最小差异。** 给出精确改前／改后内容及源基线，保留无关条款、其他 WIP 与个人覆盖。对于逐轮关闭造成的重复审批，可提议同一任务内固定模型、数据、目的地、累计预算、轮次上限及指定可恢复故障；新增凭据、配置漂移、新副作用与不明结果仍按停止条件处理。仅在实际任务适用时采用这些边界，不默认允许重试。列必要联动源、受影响消费者、检查、构建／部署、重新加载和恢复方式；修源条款，不在更多文件追加相反规则。
3. **集中取得所缺许可。** 一次列具体文件、条款、作用范围、要消除的询问及保留的例外。分别说清本任务例外、长期规则写入、live Apply、提交／推送／合并；已有许可不重问，仍须逐次批准的动作保留。获准改本项目不等于获准改全局，用户许可不突破更高优先级限制或工具权限。
4. **核对再改。** 执行前读回并比较提案基线。只有无关变化时，重做最小差异并保留其他改动；若批准条款或影响范围实质变化，只重提变化部分，不能强套旧授权。只在获准文件和条款写入；遵守工作树归属及既有源码／配置同步和部署流程，不手改生成物或直接复制到 live。
5. **验证生效。** 检查差异、必要扫描和受影响行为，读回实际源及部署结果；客户端要求新任务加载时验证该状态。源已改但未部署／加载标“待生效”，不依赖新规则执行。按[效果核验](effectiveness.md)留下旧／新来源、要消除的确认及下一正常收尾检查点；后续真实机会与安装检查分开验收。失败只暂停受影响范围，按获准恢复方式处理，不覆盖其他 WIP；不把台账“已确认”当权限。

用原私有台账的建议字段记录：问题与来源引用、提案基线、批准范围、最后验证点及实际状态（提案／待授权／源已改／待生效／已验证／暂缓或拒绝）。不另建权限数据库或修订服务。

未回复、暂缓或拒绝的提案不生效、不反复推销；若仍阻塞必要动作，说明一次准确停止点，继续独立已授权工作。没有有权修改的入口时说明正式配置途径或实际限制，不伪造文件来源，不换路径／工具／身份绕过拒绝。

## Git 链

一次任务约定可以分别列清提交、推送和合并范围，但允许前者不自动允许后者。实际仓库、远端 URL／ref、数据类别、任务／PR 关联、head／base、合并方式、期限、通知及撤销来源须可核实，不能拿示例代填。

| 阶段 | 动作前与完成后核实 |
|---|---|
| 提交 | 拥有工作树、任务及项目规则允许；复核差异与暂存区，完成必需检查，只提交本任务内容。读回完整 SHA；保留其他文件及暂存状态，不整体 stash／reset／clean。 |
| 普通推送 | 核实实际 push URL、目标 ref、提交及数据范围，按许可正常推送，读回远端 ref 关系。新目的地、新数据、强推和分支删除不包含在普通推送中。 |
| PR 就绪 | 核实本任务实际 PR、当前 head／base 与差异；最新候选的 CI、必需独审、未解决阻塞、分支保护与队列条件须满足。本地检查不代替项目要求的 CI，不自批要求独立审查的 PR。 |
| 合并／排队 | 有当前有效合并许可才执行批准方式。若项目要求每任务 owner 许可，可在任务开始或具体请求中一次取得，范围内不再重复问；跨任务取消要求须另行获准修订源规则。 |
| 读回 | 区分已推送、等待审查、已登记自动合并／排队和已合并。读取 PR 最终状态及平台实际结果 SHA，按 merge／squash／rebase 的实际方式验证目标包含关系；squash 后原 head 未必是目标祖先，不能据此重复合并。 |

等待时优先使用平台原生自动合并或合并队列；登记请求本身须获准，说明允许等待的期限及取消方式。入口不支持时，仅在当前执行中、许可有效且检查满足后普通合并；不自建后台轮询／调度、不申请新凭据或管理员 bypass。

head 新增提交、冲突修复或 base 推进后，重核内容、范围与最新候选检查；范围内常规修复不机械再申请同一许可，实质变化则暂停受影响动作。不能用旧 head 绿灯覆盖新内容，平台要求队列时按队列候选的必需检查处理。授权到期或无法核实有效性就不启用／继续排队。

非快进、访问拒绝和保护规则阻塞先查原因，不改用强推或其他身份。提交／推送／合并超时或结果未知先读回，不盲目重试；503 与安全拒绝分开记录。

撤销时停止后续依赖；已登记的原生自动合并／队列须取消并读回，停用 Skill 不会自动取消。可能已合并则先核实实际状态，无法取消就报告准确结果。revert／补救按当前许可另行处理，不擅自 reset 或 force push；不能承诺撤销授权会回滚历史。

远端分支删除另需明确授权，不能附带在合并中；若平台默认删除无法与本次合并分离，应先说明并取得所缺许可。跨任务自动合并约定应明确范围与例外；该约定及其权限规则自身的变更不能依赖该约定授予的自动合并许可批准。

仅在用户需要分阶段验证或风险要求时建议窄范围试用；用户已明确选择全局落地时，直接完成获准范围的源修改、必要检查与部署，不再设试点作为前置条件。每次按实际差异核实边界，不能从历史低分自动扩大到源码、脚本或安全配置。
